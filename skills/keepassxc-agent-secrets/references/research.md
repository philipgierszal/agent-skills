# Research: secrets in KeePassXC for AI agents

Give agents a narrow way to use secrets, never the secrets themselves. For one owner running several coding agents on Windows, the best-supported pattern is a small, separate KeePassXC database for agent-usable entries, accessed through wrapper scripts that print only results. Neither automation route is clean. `keepassxc-cli` needs the master password or a key file on every call and opens the file itself. The browser native-messaging protocol uses the already-unlocked GUI but is documented as still under development. The Claude Code sandbox does not run on native Windows, so the real controls there are deny rules, hooks, a separate vault, and approvals. Rotate on evidence of compromise, treat sync as not a backup, and rotate before cleaning up after any leak. Items marked *Inference* are my synthesis, not a source's claim; *Unverified* items were not confirmed.

## Two automation routes, each with a catch

`keepassxc-cli` is a separate process that opens the database file directly. `show -a <attribute>` prints only the named attributes, and protected ones print in clear text when named; `add -g` and `edit -g` generate passwords so none passes through arguments ([man page](https://raw.githubusercontent.com/keepassxreboot/keepassxc/develop/docs/man/keepassxc-cli.1.adoc)). Unlock options are a password prompt, a key file (`-k`) or a YubiKey (`-y`) (same source). Quick unlock is blocked when a database is opened from the command line ([KeePassXC commit](https://git.hackliberty.org/Git-Mirrors/keepassxc/commit/4f0710350fb53c25db6824f96961d8d17a29347c)). Whether the master password can be piped on stdin is **unverified**; the man page is silent on it. *Inference:* a script holding the master password or key file defeats much of the vault's purpose, so a key file must not sit beside the database.

The browser protocol lets an associated client call `get-logins`, `set-login` (update by `uuid`) and `generate-password` against the running, unlocked GUI, using NaCl box encryption and a permanent identification key stored in the database ([protocol doc](https://raw.githubusercontent.com/keepassxreboot/keepassxc-browser/develop/keepassxc-protocol.md)). That avoids both the master password in script memory and concurrent file writes. The catch: the doc calls itself unfinished, the only scripting client I found is an unaudited third-party package ([PyPI](https://pypi.org/project/keepassxc-cli/)), and per-entry approval prompts were not tested (**unverified**). A `keepassxc://by-uuid/` URL selector exists in code, but its release is unconfirmed. Secret Service (FdoSecrets) is a D-Bus mechanism ([ArchWiki](https://wiki.archlinux.org/title/KeePass)); *Inference:* it has no Windows equivalent.

Direct parsing with pykeepass has no documented corruption bug, but it writes without coordinating with the GUI ([pykeepass](https://github.com/pschmitt/pykeepass)). *Inference:* read from a copy; do not write.

## Keep secrets out of context, arguments and Git

Anything that appears in a prompt, command output or file read lands in the transcript, and Remote Control sessions sync transcripts to Anthropic's servers ([Claude Code security](https://code.claude.com/docs/en/security)). *Inference:* the safe pattern is a wrapper that fetches the secret, uses it inside one child process, and prints only a result.

Command-line arguments are readable through process listings ([CWE-214](https://cwe.mitre.org/data/definitions/214)); advice is to use stdin, a tightly permissioned file, or a secret store ([Smallstep](https://smallstep.com/blog/command-line-secrets/)). Hiding a `.env` file fails because the agent can find it, and `.gitignore` blocks only commits ([Bitwarden](https://bitwarden.com/blog/secure-ai-agent-access-with-secrets-manager/), vendor source). Claude Code's `permissions.deny` can block reads of secret files ([settings](https://code.claude.com/docs/en/settings)), but covers file tools and analyzable commands like `cat`, not scripts that open files themselves ([permissions](https://code.claude.com/docs/en/permissions)). Treat deny rules as accident guards, not a boundary (*inference*). Codex can set paths to "none" and runs a native Windows sandbox ([Codex security](https://learn.chatgpt.com/docs/agent-approvals-security)); `--dangerously-bypass-approvals-and-sandbox` removes it (same source). Claude Code's sandbox does not run on native Windows, and Read/Edit tools, hooks and MCP servers sit outside it anyway ([Sandboxing](https://code.claude.com/docs/en/sandboxing)); WSL2 is supported (same source).

For Git, GitHub push protection blocks detected secrets but is off by default, needs Secret Protection, and writers can bypass it with a logged reason ([GitHub docs](https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection)). *Inference:* add a local pre-commit scanner such as gitleaks (docs not fetched).

## Prompt injection and least privilege

Codex states that injection can make an agent fetch and follow untrusted instructions, and that web results are untrusted ([Codex security](https://learn.chatgpt.com/docs/agent-approvals-security)). Claude Code prompts for network commands by default and routes WebFetch through a separate model call ([Claude Code security](https://code.claude.com/docs/en/security)). Prompt-level defences are unreliable; architectural controls matter more ([CSA](https://cloudsecurityalliance.org/articles/the-owasp-top-10-for-llm-applications-2026-what-changed-and-why-it-matters), secondary). *Inference:* remove one leg of the combination of credentials, untrusted input and outbound network. Sessions that read email, tickets or web pages should not hold production credentials, and unattended sessions should have no sensitive entries at all.

OWASP's agentic guidance (known only through secondary summaries) recommends one identity per agent, "least agency", and approval gates for high-risk actions ([Palo Alto](https://paloaltonetworks.com/blog/cloud-security/owasp-agentic-ai-security/); [OWASP LLM06](https://owasp.org/www-project-top-10-for-large-language-model-applications/2_0_vulns/LLM06_ExcessiveAgency.html)). Anthropic's cloud design shows the target: the session holds a short-lived credential while a proxy holds the real one ([Claude Code security](https://code.claude.com/docs/en/security)). *Inference:* agent entries should be scoped service accounts in the target system, one per agent or workflow, individually revocable. Administrator credentials stay out of the agent database and need a human each time. I found no KeePassXC-specific source for read-only groups.

## Rotation, audit, backups and conflicts

NIST says not to force periodic password changes and to force a change on evidence of compromise ([SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html)). OWASP says machine secrets should be rotated regularly, ideally by automation, with the new credential tested before promotion ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)). *Inference* on order: save the new value in KeePassXC (old kept in history), set it at the service, verify a real call, then revoke the old. Set expiry dates on API-key entries and review quarterly. KeePassXC recommends at most 10 history items ([docs](https://raw.githubusercontent.com/keepassxreboot/keepassxc/develop/docs/topics/DatabaseOperations.adoc)). Audit the vault itself with Database Reports (health check, breach check), documented only through a secondary source ([BetaNews](https://betanews.com/2020/07/08/keepassxc-2-6-0)). Use Argon2id and, optionally, a key file or hardware key; back up each (KeePassXC docs, above).

KeePassXC copies the file to a configured backup destination before each save ([docs](https://raw.githubusercontent.com/keepassxreboot/keepassxc/develop/docs/topics/DatabaseOperations.adoc)). OneDrive restores earlier versions from Version history ([Microsoft](https://support.microsoft.com/onedrive/restore-a-previous-version-of-a-file-stored-in-onedrive)); recycle-bin retention is 30 days personal and 93 days work or school ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/5184463/always-keep-on-this-device-in-onedrive-what-does-i)). Administrators can disable versioning (same source). *Inference:* sync is not backup, since deletions and corruption propagate; keep a third, offline copy and test a restore quarterly. Concurrent edits produce conflicted copies, resolved with Database > Merge From Database, which matches entries by UUID and keeps the newest ([docs](https://raw.githubusercontent.com/keepassxreboot/keepassxc/develop/docs/topics/DatabaseOperations.adoc)). Merge is one-way and can drop an entry whose deletion the other copy recorded ([discussion](https://www.github.com/keepassxreboot/keepassxc/discussions/6327)); merge onto a working copy and keep the originals. OneDrive's conflict filename pattern is **unverified**. *Inference:* one writer at a time, and the file pinned "always keep on this device".

## Suspected leak: rotate first, clean second

OWASP's order is revoke, rotate, then delete the secret from code and logs, and audit who used it and when ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)). GitHub states that rotating may make history rewriting unnecessary, that rewriting does not un-leak because clones and forks keep the data, and that Support purges cached views only when rotation cannot mitigate ([GitHub docs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)). *Inference:* anything pasted into a third-party chat counts as leaked. Revoke sessions and tokens issued under the secret, read service logs for the exposure window, and write an incident note without the value.

## Conclusion

The evidence favours architecture over instruction: no agent-facing prompt rule substitutes for a vault the agent cannot read, an egress limit, and a human gate on high-value credentials. The biggest open question is the unverified browser-protocol behaviour (approval prompts, scripting on Windows), which should be tested before relying on it, with `keepassxc-cli` against a dedicated agent database as the fallback.

## Rules this supports

- Agents get a separate small KeePassXC database holding only scoped service-account entries; the owner's full vault and administrator credentials stay out of it.
- Secrets reach agents only through wrapper scripts that print results, never values.
- Never pass secrets as command-line arguments; use stdin or a child-process environment variable, and generate passwords with `-g` rather than supplying them.
- Read single attributes (`show -a`), never whole entries or protected summaries.
- Deny agent reads of secret and key files as a guardrail, and prefer WSL2 or Codex's Windows sandbox where possible.
- Keep key files and master passwords outside the database's synced folder.
- Separate sessions that read untrusted content from sessions that hold credentials; require human approval for production or high-risk use.
- Install a secret scanner at pre-commit and enable push protection on repositories.
- Rotate on evidence of compromise or when access ends; rotate machine secrets on a schedule where cheap; follow save, set, verify, revoke.
- Keep the pre-save backup, OneDrive versioning, and an offline copy; test a restore quarterly; permit one writer and resolve conflicts by merging a copy.
- On suspected leak: revoke and rotate first, review logs, then clean Git and logs; assume chat-pasted secrets are exposed.
- Test the browser-protocol route before adopting it; verify stdin unlock behaviour of `keepassxc-cli`.

## How the skill applies this (2026-11-25)

Researched for the skill with three parallel web searches and one synthesis; sources as linked above.

- **One database, not a separate agent database.** The research favours a small agent-only database. The setup the skill was written for keeps one database and gets most of the same effect differently: the adapter selects entries only by exact UUID or path and pins each service to one entry, KeePassXC asks the owner before an entry is first released, and the agents' entries are their own service accounts. A separate agent database stays the stronger option where the owner can maintain two.
- **The browser protocol is tested there.** The points marked unverified above (per-entry approval prompts, exact `by-uuid`/`by-path` selectors, create-only `set-login`) were observed working with KeePassXC 2.8.0 on Windows 11, together with one defect: an entry with an empty URL crashed KeePassXC at the approval dialog.
- **No `keepassxc-cli` for agents**, because it needs the master password or a key file in the agent's reach.
